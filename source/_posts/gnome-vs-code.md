## 前言

本文中的 GNOME 一概指 GNOME 3+ 。

笔者假定您具有对 GNOME 的充分了解。若您不了解，可通过 [GNOME官方网站](https://gnome.org) 或其他渠道了解。

标题所提出的这个判断的核心不在于 GNOME 是否提供了代码编辑能力而是 GNOME 如何处理 `统一/多样` `核心/外围``设计者/用户` 这三组关系。

VSCode 切割的很简单：核心保持(相对的)极简并让一切多样性由扩展承担。

GNOME 在最近十年的演进中完全复刻了这套逻辑。GNOME 与 VSCode 的主要区别在于它的目标对象是整个桌面体验而不是代码工作流。

## 设计固化

[Stop Theming My App](https://stopthemingmy.app/) 是理解 GNOME 品牌化转向的关键文本。

公开信明确主张：应用应当运行在它们被设计和测试过的上游 GNOME 样式表、图标和字体之下，而不应被发行版或用户的主题所改变。

libadwaita 的引入使得 GTK4 应用的外观变得难以从外部主题化，这就是他们做 libadwaita 的原因，你没法再改变 GTK4 应用的外观和感觉了。

Linux Mint 开发者为此专门 soft-fork 了 libadwaita 并推出 libAdapta 来恢复主题支持。

然而实际上即使是 libadwaita 应用也会读取系统的自定义图标包。暂时不知道这是为什么。

VSCode 做了同一件事，只是战场在 IDE 内部。

VSCode 的扩展开发者被要求使用 `--vscode-...` CSS 变量、标准 Codicons，并匹配编辑器的字体和间距，目的是让扩展“看起来像 VSCode 本身”，而不是“嵌入 VSCode 的一个网站”。

高评分 VSCode 插件的生存法则被概括为“只做一件事，并做到不干扰别人”。

两者的逻辑完全相同：平台方不再把“外观一致性”交给用户或下游去协商，而是把它编码为开发者必须服从的技术约束。

GNOME 对自定义主题的拒绝和 VSCode 对扩展样式的要求共享同一种品牌治理理性：用户所看到的界面的最终解释权归属于平台设计者。

## 应用功能单一

[GNOME HIG](https://developer.gnome.org/hig/) 的设计原则中写道：“最好的应用只做一件事，并且把它做好。”
它进一步告诫开发者：“抵制试图做一个适合所有人、所有情境的应用的冲动。聚焦于一种情境，一种体验类型。”

应用拆分实践：
Fractal 曾被计划拆分为面向小群体聊天的应用和面向大型 IRC 式房间的应用；
GNOME Crosswords 本身被描述为“实际上是两个应用”，一个是填字游戏，一个是编辑器。

> 题外话：作者今天写的时候惊奇地发现 [GNOME 应用](https://apps.gnome.org/) 里已经没有这两个应用了尽管其仍然在维护。
> 也许是因为没有拆分导致的。

这就是为什么 GNOME Circle 看上去有一大堆生态应用但实际上没什么用的原因。
相比于 KDE 的生态，GNOME 生态中单个应用的含水量平均高达 90% 。

如果以[ GNOME 自己标榜的地位](#附-gnome-官网都说了些什么)来看， GNOME 的这种原子应用的设计理念在绝大多数工作场景下都不适用。下面以最简单、基础的写代码举例。

GNOME Text Editor 是 GNOME 官方推出的文本编辑器。这个编辑器里最超出预期功能的部分可能是分页功能，除此之外的功能全都是以“我是一个文本编辑器”的理念来实现的。

Kate 是 KDE 的多功能文本编辑器。Kate 实际上已经近乎于一个完整的 IDE ，内置了诸如终端、工作区、Git 管理、LSP 等功能。另外值得注意的是 Kate 的启动速度比 GNOME Text Editor 快得多。

这意味着绝大部分工作实际上都可以在一个 Kate 内完成。而在 GNOME ，你可能需要:
1. 使用 GNOME Text Editor 编辑文件
2. 打开一个 [Ptyxis](https://flathub.org/zh-Hans/apps/app.devsuite.Ptyxis) 终端进行代码验证
2. 使用 [Commit](https://apps.gnome.org/zh-CN/Commit/) 编写 Commit
3. 使用 [gitg](https://flathub.org/zh-Hans/apps/org.gnome.gitg) 进行提交

当然你也可以直接使用 GNOME 官方推出的超级 IDE [GNOME Builder](https://apps.gnome.org/zh-CN/Builder/) 。相信我，你不会想要打开它第二次。

> 那相对于 VSCode 呢？

VSCode 的核心设计决策几乎是这句话的镜像。VSCode 团队被描述为刻意选择一个“非常节制而平衡的”定位：编辑器 + 代码理解 + 调试；大部分针对特定语言和技术的功能由第三方插件提供，核心始终保持精简。团队对超出定位范畴的功能请求“基本都被婉拒或者转交到第三方插件项目”。一个桌面环境把邮件、日历、任务、聊天拆成不同的“核心应用”，和一个编辑器把语言支持、调试器、版本控制界面拆成不同的扩展，在功能哲学上是同一种操作的两种尺度：**核心不承担完整工作流，只提供“槽位”和基础体验；具体的、多样的、情境化的能力，被推向外部**。

## 设计界面大拆大改

某位 GNOME 团队成员在 2019 年的邮件列表总结中提到移除托盘的目标之一是“向应用开发者施加压力，让他们放弃过时的 app-indicator 模型”。

这一设计决策的后果是，守护进程类应用失去了在界面中被感知的常规位置；用户和下游厂商不得不通过扩展来恢复基础功能，Ubuntu 甚至默认搭载 appindicator 扩展。
更关键的是，工作区在默认状态下并不承担“显示所有正在运行的应用”的功能。

一位参与讨论的开发者指出，概览的本职应当是展示运行中的 GUI 应用，如果它不展示那些没有窗口的守护进程应用，“它就没有在做它的工作”。

所以 GNOME 后来端上来了一个 Flatpak 后台应用列表组件来替代这个托盘。显然并不是所有 GNOME 用户都使用 GNOME OS 这类唯一包管理是 Flatpak 的发行版的但 GNOME 开发者似乎是这么认为的。
所以如果你在纯原版 GNOME 中想要运行一些带有驻留功能的应用比如 QQ 你只能用 Flatpak 安装它们。

另外 Linus Torvalds 曾因为设计原因专门批评过 GNOME 3 然后从 GNOME 2 直接换成了 Xfce 而不是 GNOME 3 。

在设计上，GNOME 和 VSCode 的方向是一致的：界面被设计为一座工作区，而不是一个仪表盘。托盘所代表的持续状态感知、工作区中所有应用的同时在场，这些都被视为对当前任务的干扰。桌面和 IDE 在这里共享同一种注意力经济学。

VSCode 也有很多这类设计但它是可以配置的。你当然可以在 VSCode 里关闭各种各样的状态栏和面板之类的只剩一个编辑界面，但你也可以不关闭。

而在 GNOME 你想恢复托盘功能？那对不起，**快滚去用扩展吧！**

## 隐藏外围功能

GNOME 自带的设置简陋无比， GNOME 开发者认为这是一种“分层”。
没有能力的用户通常也不需要修改那些高级设置项，而有能力的用户自有办法。

但你连个字体都不让用户改是不是过分了。

所以这一部分 GNOME 的问题在于它“缺乏人们真正关心的配置”，背后的原则是“相信我们的设计哲学，不要试图改变它”，但一旦 Tweaks 这类工具允许改变，这个原则就被削弱了。

> 我很想在这里放一首《我相信》但是主题没有音乐播放器。

GNOME 扩展也有同样的问题。首先你要有一个浏览器来访问 GNOME 插件商店，然后你需要一个 `gnome-browser-connector` 的神秘程序来让浏览器扩展可以与 GNOME 通信，然后你才能安装插件。另外如果你想管理插件设置，要么从插件商店里进入（为什么插件商店还要负责设置？这其实不符合上文提到的设计哲学）要么再单独安装一个插件管理器，否则你就只能捏着鼻子用 dconf 改了。

VSCode 把同一套分层做得更加彻底且坦率。图形化设置界面呈现的是常用选项，而活动栏、状态栏、编辑器 minimap、AI 提示等大量 UI 层面的控制，被放置在 `settings.json` 中；有些隐藏操作甚至必须手动编辑 JSON 才能完成。扩展的获取同样依赖一个外部的 Marketplace。**“默认界面保持干净，深度控制外置到文件、CLI 或独立工具”**，这是 GNOME 和 VSCode 共享的界面治理语法。区别在于，VSCode 的用户群体对此有更高的容忍度，因为“编辑 JSON 配置”本身就是他们工作身份的一部分；而 GNOME 把同样的模式施加给普通桌面用户时，摩擦被成倍放大。但摩擦的存在并不否定模式本身：两者都把“完整的控制权”定位为一种需要额外步骤才能抵达的外围状态。

## 社区边缘化

上述四条汇聚成一个更底层的姿态。
本文借用日料中的“Omakase”（お任せ）来解释：设计者替用户做出选择，用户被邀请信任并接受，而不是参与定义。

GNOME 的设计使命被学术研究描述为一种“控制 GNOME 计算宇宙的欲望”，通过推广项目、持续论证和意识形态邀请来维系其宏大愿景。
HIG 中的“减少用户努力”原则要求“如果某件事可以自动完成，就自动完成它”，其合理延伸正是减少用户需要做出的选择——包括减少用户被允许做出的选择。

当然实际上这套理念只能在 Windows 上行得通毕竟真正需要你手把手喂的小白痴压根不会来用 Linux 发行版。

VSCode 的模式是：核心团队替用户决定了什么是编辑器该做的事，然后把编辑器不该做的事全部推给扩展。
但 VSCode 的扩展生态至少在名义上保持开放。任何人都可以写扩展，没有什么设计哲学审查。

GNOME 的困境在于，它在采纳 Omakase 姿态的同时，未能为被它推到外围的社区提供一个稳定的参与界面。
GNOME 长期不提供稳定的扩展 API，扩展通过 monkey-patch 直接修改 Shell 代码，其理由是“扩展开发者自由”，但后果是每次 GNOME 版本更新都会大面积破坏扩展，维护一套长期可用的扩展被形容为“不可持续”。
扩展开发者感到被低估和利用，而核心团队与用户反馈之间的沟通又被批评为“轻蔑且缺乏回应”。于是 Omakase 变成了单向的：**设计者端上菜品，社区既不能改菜单，也很难稳定地给厨房递一张新菜谱**。

如果你不太能想到这种修改方式的难度可以类比于一边开车一边换轮胎。

VSCode 证明了一个平台可以靠极简核心和外部扩展获得巨大成功，但它的扩展接口是**受控的、文档化的、有市场规则的**；
GNOME 吸取了“核心极简、功能外置”的果实，却在扩展治理上长期停留在非正式的、依赖志愿者善意的状态。
两者共享同一套平台 IDE 的政治经济学，但 VSCode 至少为扩展开发者提供了一个可预期的交易结构，而 GNOME 把社区置于一种既被需要又被管理的尴尬位置：

如果以 API 的角度看 GNOME ，那么实际上 GNOME 一直都是发布候选版本。

## 总结

以上就是为什么 GNOME 的竞品是 VSCode 的论证。

简单的说，GNOME 中的“应用”正在变成独立的功能单元，它们之间的工作流衔接（通知、状态、后台任务、跨应用导航）被交给桌面或者扩展。

VSCode 则把语言智能、调试、测试、版本控制界面等附加功能全部外包给语言服务器和扩展，核心只保留编辑器和协议。

如果你把 GNOME 当成一个 IDE ，那它还算过关。如果你把 GNOME 当成一个桌面环境，那它是毫无疑问的烂。

两者都把自身定位为一个**运行时容器**，而不是一个完成了的集成环境。

当桌面环境开始用 IDE 的方式治理自己的边界——定义什么属于核心、什么必须外挂、外挂必须遵循什么外观——它就在设计政治的意义上，成了 VSCode 的同构体。它们争夺的不是同一批功能，而是同一种**平台作者的身份**。

## 附: GNOME 官网都说了些什么

本节建议阅读时参照 [GNOME官方网站](https://gnome.org) 进行对照。

首先 GNOME 官网打开第一句是“一个适用于每个人的独立计算平台”。然后这句话完全是狗屎因为他是软件而不是什么笔记本电脑或者工作站之类的。

然后往下滑是一个“一种更优雅使用您计算机的方式”：

> 按下 Super 键 在任何时候获得概览，切换或启动应用，搜索您计算机上的任何东西。像魔法一样。

我操难道 2026 年还有什么桌面环境或者操作系统没有一个概览吗？这是卖点吗？显然首先 GNOME 假定了他们的用户可能是第一次使用智能电子设备。

再往下滑是一个“喘息的空间”：

> 按您的需要将工作分布到多个工作区。

我操难道 2026 年还有什么桌面环境或者操作系统没有工作区吗？这是卖点吗？显然 GNOME 又一次假定了他们的用户可能是第一次使用智能电子设备。

最后是一个“开箱即用”和“生态系统”：

> GNOME 带着用于您所有计算所需的应用而来。它们简约且一致，因此一旦您熟悉了其中一个就会感觉其他也很熟悉且直观。

这句话的后半句是真的。前半句则取决于发行版。当然绝大多数预装桌面环境包括KDE的发行版都恨不得把桌面环境生态里的所有应用都塞进去就好像甲方觉得应用不够大于是乙方往里塞猫和老鼠一样。
